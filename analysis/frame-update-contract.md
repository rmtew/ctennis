# Source frame-update contract

This document specifies the source cartridge's update order and RAM effects for a gameplay interrupt. The phase order is derived from the reconstructed Z80 source. A bounded active-play cadence and input observation is recorded in [source-timing-baseline.md](source-timing-baseline.md). Addresses are CPU addresses. It is an implementation contract for the Amiga port where effects are settled; conditional paths still needing verification are marked explicitly. See [static-rom-review.md](static-rom-review.md) for the whole-image partition and byte classification.

The translated body is executable in [source_gameplay_slice.py](../scripts/source_gameplay_slice.py): snapshot of the prior sprite buffer, scoreboard VRAM writes, input selection, score gate, lower player, upper player, ball dispatcher, player movement/sprite construction, IRQ counters, audio tick and pending VDP-register writes, in that order. [source_input_movement.py](../scripts/source_input_movement.py) takes the bytes returned by the ROM's input readers `$087E/$0887` as explicit inputs; raw SG/SC port scanning and actual VDP/PSG devices are outside this model. [source_audio.py](../scripts/source_audio.py) interprets ROM sound commands and returns ordered PSG bytes.

## Interrupt entry and phase order

The IM 1 vector at `$0038` reads VDP status from port `$BF`, loads a callback pointer from `$C000-$C001`, and calls it via `$0049`. Setup installs `$0699` as that callback through `$001B`. The Z80 swaps its primary/alternate register sets around the callback. A VDP interrupt is therefore the gameplay update trigger. A controlled SC-3000 run measured one update in each of 60 consecutive video intervals at 59.922738 Hz; this does not establish every mode or a PAL frame cadence.

| Order | Entry | Source-visible contract |
| ---: | --- | --- |
| 1 | `$046F` | Copy 40 bytes of sprite attributes from RAM `$C010-$C037` to VDP VRAM `$3B00-$3B27`. This uploads the buffer built on the preceding update. |
| 2 | `$06EB` | Process pending status/scoreboard work. `$06F1` examines `$C042` bit 7, builds a 3-tile status from `$0725`, and uses `$C071` as a countdown/transition latch. `$073A` consumes `$C042` bit 5, selects one of three 5-tile mode strings from `$07A2`, and draws point and game records from `$0816` and `$07B1`. The scoreboard is conditional, not redrawn unconditionally. |
| 3 | `$0832` | Normalize controller/keyboard input to `$C053` and `$C056`. `$C03D` bit 2 clears both and returns. With bit 7 clear, `$087E` reads game input and splits low nibble to `$C053`, input bits 4-5 to `$C056`. With bit 7 set, `$0887` supplies additional keyboard input before combining the fields. |
| 4 | `$094E` | Resolve pending point/state transition from `$C03C`, `$C039`, `$C042`. The scoring branch requires `$C03C` bit 6 and `$C039` bit 7. It can update `$C03E/$C03F` point codes, `$C040/$C041` game counts, `$C03D` mode/match bits, `$C038` flight state, player/ball flags, and `$C06C` transition counter. Because this runs before the ball update, an out-of-area flag set in phase 7 is scored on a later interrupt. |
| 5 | `$0B29` | Lower-player phase dispatcher on bits 7 through 1 of `$C03A`. Serve setup copies the 7-byte vector at `$0B73` through `$1760`; contact path `$0BF3` uses shared geometry `$1770`, then height bounds. A successful return writes new launch values around `$C057-$C05F`, marks `$C038` bit 7, updates `$C043` animation state, and changes the lower phase. |
| 6 | `$0E54` | Upper-player counterpart on `$C03B`, using serve vector `$0EA0`, contact `$0F19`, and related trajectory tables. It can replace the ball launch/phase before phase 7. This is source order, not simultaneous player resolution. |
| 7 | `$11A0` | Ball dispatcher on `$C038`: bit 7 copies six launch bytes `$C057-$C05C` to flight bytes `$C060-$C065`, zeros step `$C066`, and changes to active bit 6; active flight advances through `$12CE`, checks net/court/height, and may set `$C039` bit 7 and stop. Bit 5 hides the ball by placing `$C2` in ball/sprite Y fields. |
| 8 | `$13B9` | Move lower/upper players via `$1404/$145D`, advance animation via `$14A7/$14B3`, build both player sprite records via `$10E9`, and copy four ball sprite-attribute bytes to one of `$C010/$C020/$C030` according to ball Y relative to the players. Movement is gated by `$C039` bit 2 and each player's animation bit 7. The new buffer is uploaded in phase 1 of the next update. |
| 9 | `$06B1` | Increment `$C06B` and the subsequent counter bytes with their overflow rule; decrement audio countdown `$C083` and call `$17C5` at zero. If `$C002` bit 7 is set, update VDP register 1 or 2 according to bits 0/1, then clear bit 7. |

The order creates observable one-update boundaries. Rendering uses the prior sprite buffer; input is read before movement; scoring precedes a new flight step; a player contact can change the ball trajectory before that step; and audio/counters are serviced last. Preserve this ordering even if the Amiga code uses a different interrupt or rendering mechanism.

## Gameplay state and transitions

| RAM | Source-level role | Writers/readers needed for the port |
| --- | --- | --- |
| `$C03D` | Mode/status flags. Bits 2, 3, 4, 6, 7 affect input, side/serve setup, score attribution or match completion. | Setup `$0242`, input `$0832`, score `$09EC/$0A0D/$0A4F`, serve reset `$0AA2`, movement `$148C`, AI `$162D`. Exact user-facing mode labels still need correlation. |
| `$C03C` | Game/score phase flags. Bit 6 enables score resolution; bits 5/4 are timed transitions; bit 7 has a distinct pending path. | `$094E-$0AA1`. |
| `$C038` | Ball flight dispatcher flags: bit 7 launch pending, bit 6 flight active, bit 5 hidden/stopped. Other bits influence flight/net behavior. | Hit paths, `$11A0-$12CD`, score reset. |
| `$C039` | Point/ball outcome flags. Bit 7 requests scoring; bit 1 records contact/bounce progression; bit 0 is set at net vicinity; bit 6 changes score attribution. | `$094E-$0A78`, `$1298`, `$1383`, contact routines. Do not collapse to a single boolean. |
| `$C03A/$C03B` | Lower/upper player phase bitfields, dispatched highest bit first. | `$0B29/$0E54`; serve starts at bit 7, followed by timed/contact/AI phases. |
| `$C03E/$C03F` | Point-code pair. | `$09CE-$0A3D`, display `$0805`. Codes 0/1/2 advance, code 3 or 4 can award a game, code 5 is deuce, code 6 is the opposing blank/display state during advantage. These tennis names are inferred from transition logic. |
| `$C040/$C041` | Game-count pair, indexing 12-byte display records. | `$0A3F-$0A5D`, `$0781`. Reaching six sets `$C03D` bit 6. |
| `$C043/$C044` | Lower/upper animation and movement flags. Bit 7 blocks movement; bits 3/4 control animation sequence. | Hit/serve paths, `$1278`, `$1404/$145D`, `$14A7/$14B3`. |
| `$C045/$C046`, `$C049/$C04A` | Upper and lower player Y/X. | Movement and sprite builder. `$C047/$C04B` select sprite descriptor/appearance. |
| `$C053/$C056` | Packed normalized input fields. | `$0832` producer; player state and movement consumers. `$162D` may synthesize the direction nibble for AI. |
| `$C034/$C035`, `$C04D/$C04E` | Ball court-plane Y/X and sprite Y/X. | `$12CE` updates them, `$1770` compares ball to player contact geometry, `$13B9` emits sprite attributes. |
| `$C057-$C05C`, `$C060-$C066` | Six-byte launch vector, six-byte active flight vector and flight step. | Serve/hit/trajectory arithmetic, `$11C5`, `$12CE`. Keep signed-magnitude/high-bit conventions from source arithmetic until formally decoded. |
| `$C067-$C06A`, `$C073-$C076` | Arithmetic scratch and AI target fields. | `$1554-$1753`; values can be reused by several routines within an update, so porting should preserve call order and not treat scratch as persistent gameplay state without proof. |
| `$C06B-$C071`, `$C082/$C083` | Interrupt counters, scoreboard countdown and audio reload/countdown. | `$06B1`, `$06F1`, `$17C5`. |

The contact helper at `$1770` accepts `abs(ball court Y - player contact Y) < 4` and `abs(ball court X - player contact X) < 17`; each player path also requires `0 <= ball court Y - ball sprite Y < 29`. Flight at `$12CE` calculates court and sprite positions separately. The out-of-area branch at `$120E` sets `$C039` bit 7, clears `$C038` bit 6, and sets bit 5. The `$1383` net-vicinity routine checks `abs($C034 - $6E) < 3`, sets `$C039` bit 0, and flips the sign bit of `$C061` once. Precise on-screen court interpretation and net collision outcome should be checked later.

The point routine selects one score cell from `$C03E/$C03F` using `$C042` low bits, `$C039` bit 6, and `$C03D` bit 4. It then follows the point-code state machine described in the whole-ROM review. Game award increments one of `$C040/$C041`, clears both point bytes and current ball motion, marks redraw, and sets player animation flags. A later timed transition resets positions and serve state. This is enough to implement a source-faithful state machine, while the user-facing side labels and every service alternation still need annotation.

## Service, AI and trajectory details

`$0242-$025C` derives `$C03C` from `$C03D`: mode bit 2 produces `$83`; mode bit 7 produces `$80`; otherwise bit 4 selects `$82` versus `$81`. In the player handlers, `$C03C` bit 1 gates automatic lower service and bit 0 gates automatic upper service. In the movement/AI phases, bit 6 gates synthesized directions, but that bit is set and cleared by the scoring phase, so it must remain separate from the low player-selection bits. The mode-to-human-player labels are still inferred, but the bit mapping is exact.

Lower service is a state machine at `$0B29-$0BEB`. Bit 7 of `$C03A` copies the 7-byte lower serve vector `$0B73-$0B79` to `$C060-$C066`, adjusts its horizontal field by lower-player X through `$1760`, clears `$C039` and `$C06C`, then selects phase bit 6. In phase bit 6, `$0B7A` advances the flight representation and attaches ball X to lower X plus `$14`. If `$C03C` bit 1 is set, the serve waits for `$C06C >= $50`; otherwise it waits for a nonzero low-two-bit action result from `$C056` through `$1498`. The next phase sets `$C043=$F0` and `$C03A=$20`. At `$C06C=$10`, `$0BBC` sets lower animation bit 7 and constructs a randomized launch; at `$20`, it arms upper animation/phase; at `$31` or later, it clears lower animation bit 7 and changes lower phase to `$11`. The upper path at `$0E54-$0F18` is analogous: it uses upper serve vector `$0EA0-$0EA6`, attaches ball X to upper X minus 4, writes `$C044=$F3`, and arms the lower side at the corresponding stage.

The random launch construction at `$0DCE-$0E2A` (lower) and `$107B-$10D6` (upper) fills `$C05A-$C05F`, sets `$C038=$80`, and runs arithmetic `$1554` to derive the six-byte launch vector `$C057-$C05C`. Each of the three selected 9-byte tables has four thresholds followed by five possible output values. `$0E2B` calls the 8-bit PRNG, uses `$161C` to compare against those thresholds and choose one output, then adds a second random value masked with `$0C`. With probability selected by `random >= $E0`, a special trajectory replaces two fields and sets `$C038` bit 3. `$C03D` bit 3 mirrors/adjusts one field. The precise geometric interpretation of each vector byte remains provisional; the byte operations and table selections are implementation requirements.

The AI paths at `$0D61-$0DAD` and `$102A-$1077` are symmetric. In their setup phase they call `$167C` to predict two candidate ball-intercept coordinates from the launch/flight fields; a PRNG value at least `$F0` swaps the candidates. `$16FA` adjusts a candidate relative to the player's X, `$0DC2` adds a signed random offset in `[-7,7]`, and the result is stored in `$C073/$C074` for lower or `$C075/$C076` for upper. In their tracking phase, `$162D` compares those targets to player Y/X and synthesizes direction bits into `$C053` when `$C03C` bit 6 permits AI control. When target direction becomes zero, another signed random offset with magnitude `$10-$1F` is used to shift the opposite target. The sign selection reads the Z80 refresh register `R` bit 0 at `$0DB9-$0DBD`; a port must explicitly choose how to reproduce that source-dependent entropy if identical trajectories are required. The PRNG at `$1754` itself is `seed = (5*seed + 1) & 255` using `$C072`.

On a valid player contact, both handlers clear active flight, select a new launch from contact position, optional input/AI action, and trajectory arithmetic, and set `$C038` bit 7. The later ball phase copies the newly calculated six-byte vector to `$C060-$C065` and resets step `$C066`. `$12CE-$1382` computes court-plane and displayed ball coordinates separately using the signed high-bit fields, multiplication `$151E` and division `$152B`; `$121C-$1286` handles bounce/contact reflection by rewriting trajectory fields. This exact fixed-point arithmetic should be translated instruction-for-instruction before simplifying its geometry.

## Animation-table index audit

`$14CD-$14DB` masks `$C043/$C044` with `$07`, multiplies by nine, and addresses records beginning at `$14FA`. Static writer inspection narrows the low bits: initialization `$0AB3/$0AB6` writes 0 or `$20`; the lower serve writes `$F0`, while the upper serve writes `$F3` at `$0ED5`; return paths at `$0CA2/$0FD6` take `$0CDA`, which returns `$F1` or `$F2`; `$127D-$1284` preserves the low five bits; and `$14BD-$14F9` changes bits 3/4 only. Thus normal ROM-controlled writes supply indices 0-3, matching the four records. Indices 4-7 require an out-of-model RAM value. The previous concern about routine indexing into code is **resolved for these audited writers**, conditional on no unreviewed alias/corruption. A later runtime watch is useful, but is not required to classify `$151E` as code.

## Audio and display boundary

The three 14-byte audio records start at `$C085`, `$C093`, `$C0A1`, with stream buffers at `$C0AF`, `$C0CF`, `$C0EF`. On countdown zero, `$17C5` processes records in reverse order (2, 1, 0), interprets stream commands via `$185B`, emits PSG values through port `$7F`, then reloads `$C083` from `$C082`. The audio engine is part of the source update, but its exact audible cadence should be checked with targeted reference playback when the port produces sound. The scoreboard writes name-table VRAM; sprite upload writes `$3B00-$3B27`. The Amiga renderer must reproduce the resulting visible state rather than emulate the VDP ports mechanically.

## Remaining checks before calling the port equivalent

The phase contract originated in static analysis; the separate [source timing capture](source-timing-baseline.md) now establishes a bounded active-play cadence and same-interval input response. The later [annotation audit](annotation-audit.md) records the completed instruction-level label and comment pass. The court-layout reader is proved for `$0645-$0668`; only 14 byte-emitted positions lack direct consumer evidence (`$1FFB-$1FFF` and nine inter-vector padding bytes). Remaining checks include mode/side labels and ambiguous flag semantics, other update regimes, and reachable state snapshots and presentation timing against the Amiga implementation. Do not substitute branch coverage for source analysis.
