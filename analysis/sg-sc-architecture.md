# SG-1000 / SC-3000 cartridge architecture for Champion Tennis

This is the hardware and emulator reference for interpreting the G-1009, MPR-5439 cartridge. It distinguishes the SG-1000 execution contract, the SC-3000 keyboard extension, Gearsystem 3.9.18's implementation, and facts demonstrated by this ROM. The authoritative gameplay target remains the SG-1000 cartridge. A plausible Z80 instruction or a byte-exact rebuild alone is not evidence that an address contains code. For current cartridge-specific classifications and open work, use [the static review](static-rom-review.md) and [worklog](../WORKLOG.md); some historical capture descriptions below predate those reviews.

## CPU and address spaces

The cartridge runs on a Z80. The CPU has a 64 KB address space, a separate 8-bit I/O port space, and interrupt entry at `$0038` in IM 1. VRAM is **not** CPU-addressable RAM: the CPU transfers bytes through VDP ports. The SN76489 PSG is likewise controlled through an output port. MAME's SG-1000 board notes give a 3,579,545 Hz CPU/PSG clock for the NTSC machine; frame rate and actual game-update rate are different quantities and must be measured separately. [MAME SG-1000 driver](https://github.com/mamedev/mame/blob/master/src/mame/sega/sg1000.cpp), [TI TMS9918A data manual](https://www.bitsavers.org/components/ti/TMS9900/TMS9918A_TMS9928A_TMS9929A_Video_Display_Processors_Data_Manual_Nov82.pdf).

| Z80 address | SG-1000 interpretation for this 8 KB image | Consequence for disassembly |
| --- | --- | --- |
| `$0000–$1FFF` | The 8,192 physical cartridge bytes, offset equal to CPU address here. | Only this range belongs in the rebuildable ROM source. |
| `$2000–$7FFF` | Gearsystem mirrors a smaller cartridge by `address % ROM_size`, so this image repeats every `$2000`. | A trace PC here is an alias of a physical ROM offset; do not invent extra image bytes. |
| `$8000–$BFFF` | Expansion/cartridge-dependent space; Gearsystem returns `$FF` without corresponding RAM or larger ROM. | Inspect the actual cartridge hardware before assigning data here. |
| `$C000–$FFFF` | 1 KB SG-1000 system RAM mirrored every `$0400` in Gearsystem and MAME. | Normalize a CPU RAM address to `$C000 + (address & $03FF)`; `$C400` is an alias, not extra RAM. |

Gearsystem's pinned [SG1000MemoryRule.cpp](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/SG1000MemoryRule.cpp) implements that map. MAME independently models 1 KB SG-1000 RAM but 2 KB for the **SC-3000** configuration. The bundled Gearsystem `mcp/resources/hardware/sg1000.md` is marked `draft` and claims 8 KB system RAM; do not use that claim for this project. Gearsystem's [Memory.cpp](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/Memory.cpp) copies physical cartridge bytes into its backing map; the SG-1000 memory rule performs mirroring on CPU reads. An MCP memory-area dump and a CPU bus read can therefore answer different questions at mirrored addresses.

The ROM begins `DI; IM 1; LD SP,$C400; JR $004A`. `$C400` aliases `$C000` on the SG-1000 RAM bus. The interrupt vector at `$0038` eventually jumps through a target held at `$C000`; the active callback can vary by phase. These are ROM observations, not generic requirements of every cartridge. [ROM evidence map](rom-map.md).

## I/O map used by this ROM

MAME's [SG-1000/SC-3000 driver](https://github.com/mamedev/mame/blob/master/src/mame/sega/sg1000.cpp) and Gearsystem's pinned [SmsIOPorts.h](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/SmsIOPorts.h) agree on the device families at these ports. Hardware address decoding has aliases; the table lists the addresses the game uses or is expected to use, not a claim that each is the only legal address.

| Port | Direction | Device and meaning | ROM evidence / caution |
| --- | --- | --- | --- |
| `$BE` | read/write | VDP data; sequential transfers to/from the selected 14-bit VRAM address. | `$0277`, `$027F`, and `$029D` use it. A `read_memory` of Z80 RAM does not reveal these transfers. |
| `$BF` | write | VDP control: two-byte VRAM address or register command. | `$0287–$0293` writes the low/high command bytes; `$06D6–$06E8` also writes control values. |
| `$BF` | read | VDP status, including VBlank interrupt and sprite flags. | The interrupt path reads it at `$003D`; startup reads it at `$005A`. Reading status has side effects on VDP flags/latch. |
| `$7F` | write | SN76489-compatible PSG command/data byte. | `$1974` mutes tone channels; `$197D` and `$198A` write sound values. Gearsystem also accepts writes throughout `$40–$7F`. |
| `$DC`, `$DD` | read | Controller ports / optional keyboard peripheral. Controller bits are active low. | Input scanner at `$0938` and `$0949`; meaning depends on whether an SC-3000/SK-1100 keyboard is actually attached. |
| `$DE`, `$DF` | write/read | SC-3000/SK-1100 keyboard peripheral control and probing. | Startup probes `$DE` at `$01F4–$01FB`; input scan writes `$DE` then reads `$DC` or `$DD`. `$DF` is also written at `$007A`. Gearsystem's SG mode does **not** implement the keyboard output path. |

For Gearsystem controller mode, [Input.h](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/Input.h) maps `$DC` bits 0–5 to P1 up, down, left, right, button 1, button 2; bits 6–7 carry P2 up/down. `$DD` bits 0–3 carry P2 left/right/buttons; bit 4 can represent reset. The controller API uses logical `press`/`release`; the register presented to the game is low-active. The ROM input routines combine controller and conditional keyboard scans, so a controller event must be checked at the port-read and normalized-state levels, not inferred from a screenshot.

## VDP and graphics data flow

The TI TMS9918A family has its own 16 KB VRAM, eight write-only registers, a read-only status register, a fixed-color palette, background tables, and a sprite subsystem. Its visible active area is 256 × 192 pixels. A VDP control-port write is interpreted in pairs: first the low eight address bits, then high address bits plus command bits; a register write uses the second byte's register-command form. A data-port transfer advances the VDP address. The exact VRAM table bases depend on register values and graphics mode, so decode those before calling any ROM byte stream a tile, color table, name table, or sprite. The status register's VBlank, collision, and fifth-sprite information may affect control flow; a read also changes VDP state. [TI data manual](https://www.bitsavers.org/components/ti/TMS9900/TMS9918A_TMS9928A_TMS9929A_Video_Display_Processors_Data_Manual_Nov82.pdf).

The current ROM listing already gives a concrete path to follow. `$0287–$0293` constructs a VDP address command from `HL` and leaves port `$BE` in `C`. `$029D–$02B0` selects a VRAM destination, then reads sequential bytes from CPU address `HL` and writes them to `$BE` until `BC` reaches zero, with interrupts disabled during the bulk copy. Thus a caller's `HL`, `DE`, and `BC` identify a source span, VRAM destination, and length. For example, `$00AD–$00B6` supplies `HL=$19CC`, `DE=$1800`, and `BC=$0400` to this copier: physical ROM `$19CC–$1DCB` is a **VDP transfer source**. Its internal graphics format and any subregions still require the VDP register state and destination analysis. Other code prepares bytes in RAM before copying them to VRAM; the source bytes may be encoded assets rather than literal screen patterns. This producer-to-consumer chain is stronger code/data evidence than whether an emulator executed a byte as an instruction.

The first reset-to-title hardware capture now confirms that example: title VRAM `$1800–$1BFF` equals ROM `$19CC–$1DCB` byte for byte, with register 6=`$03` selecting the sprite-pattern base. It also finds ROM `$1C4C–$1F93` in all three Graphics II background-pattern banks. A 16-byte packed stream at ROM `$01C3–$01D2` expands into matching color-table bytes in each band. Register 2 starts at `$0E` (name table `$3800`) but changes to `$0F` (title name table `$3C00`); table addresses must therefore be recorded per phase. See the [ROM map's capture evidence](rom-map.md) and `scripts/check_vram_sources.py`.

For each graphics path, record: the controlling VDP register values and mode; destination VRAM address; source ROM/RAM span; length and transform; when it runs; and what changes onscreen. Export VRAM and the register set at the same checkpoint. Do not identify tile or sprite boundaries from appearance alone.

## PSG and sound data flow

The SN76489 family has three tone channels and one noise channel, each with attenuation control. Writes use latch/data byte formats; a stream in ROM is not necessarily a raw PSG byte stream because game code may turn note/event data into register writes. [TI SN76489AN data sheet](https://map.grauw.nl/resources/sound/texas_instruments_sn76489an.pdf), [Gearsystem Audio implementation](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/Audio.cpp).

In this ROM, `$1787–$17B8` initializes three 14-byte RAM channel records from a 12-byte ROM template at `$17B9–$17C4`, and `$17C5` updates the channels. `$1974`/`$197D` are PSG output routines. The observed pointer near `$19BC` leads to sound-event reads at `$19BD` and `$19C0`, but neither the stream's end nor its encoding is established. Decode the record fields and the write formatter before classifying the rest of that region as sound data. [ROM evidence map](rom-map.md).

## Input hardware distinction: SG controller versus SC keyboard

The SG-1000 can use joysticks. The SC-3000 includes the keyboard functionality represented by the SK-1100 peripheral on SG-1000. MAME's [SG-1000 driver](https://github.com/mamedev/mame/blob/master/src/mame/sega/sg1000.cpp) routes `$DC–$DF` to the optional peripheral, and its [SK-1100 implementation](https://github.com/mamedev/mame/blob/master/src/devices/bus/sg1000_exp/sk1100.cpp) uses an 8255 PPI: `$DE` selects a keyboard row via port C bits 0–2, while `$DC`/`$DD` read row data. MAME's key matrix places `Del/Ins` at row 3, port A bit 4 and `Func` at row 5, port B bit 3. Those placements are a useful cross-check for the game's printed `1PLAY ... INS/DEL` and `2PLAY ... FUNC` instructions, but the cartridge's exact selection logic remains to be traced.

Gearsystem 3.9.18 selects `SmsIOPorts` for SG-1000 media. In that implementation `$DC/$DD` are controller reads, while the `$DE/$DF` keyboard-output branch is compiled out (`#if 0`), and the exposed MCP input tools offer controller buttons but no SC keyboard keys. Therefore Gearsystem can show the SG controller-facing execution path but cannot by itself validate a keyboard-dependent one-player/two-player selection. The earlier court screenshots are not proof that the advertised SC keyboard mode started. This is an emulator capability boundary, not a property to assume of the physical cartridge. [Gearsystem core](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/GearsystemCore.cpp), [I/O implementation](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/SmsIOPorts.h), [MCP tools](https://github.com/drhelius/Gearsystem/blob/3.9.18/MCP_README.md).

Local MAME 0.289 now supplies the missing keyboard-control capability. Its SC-3000 software-list launch loads the verified `champtns` image, exposes `Del  Ins  DELETE` on `:sgexp:sk1100:PA3` mask `$10` and `Func` on `:sgexp:sk1100:PB5` mask `$08`, and permits Lua `field:set_value` / `field:clear_value` injection. A Del/Ins press requested after frame 30 changed the emulated PA3 row from `$FF` to `$EF` at frame 31; releasing after frame 60 restored `$FF` at frame 61. This proves keyboard injection, not match entry or gameplay behavior. The exact invocation and archive provenance are recorded in [WORKLOG.md](../WORKLOG.md).

## Interrupts, timing, and Gearsystem observations

The VDP can assert a frame interrupt; with Z80 IM 1 the CPU enters `$0038`. This ROM's handler reads VDP status at `$003D`, uses the callback address at `$C000`, and returns with `EI; RET`. `$06B1` advances counters and conditionally calls the audio updater. None of that alone identifies a full gameplay tick or proves one update per video frame. Measure consecutive completed updates at a game-state checkpoint, recording Z80 T-states and VDP frames. Gearsystem 3.9.18's [definitions.h](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/definitions.h) uses NTSC 3,579,545 Hz / 262 lines and PAL SG-1000 3,580,000 Hz / 313 lines with 228 T-states per line; its media report for this cartridge currently says `is_pal=false`. Those are **emulator configuration values**, not measured game speed.

Gearsystem MCP exposes separate CPU memory, VRAM, VDP register/status, and PSG views. `debug_step_frame` with `mode: "sync"` stops after requested VBlanks; it does not stop after a game update. `set_trace_log` can capture `vdp.registers`, `vdp.data`, `psg.tone`, `psg.volume`, `psg.noise`, `input.reads`, and CPU instructions. `read_memory`, `get_vdp_registers`, `get_vdp_status`, `get_psg_status`, and execution/read/write breakpoints can anchor a producer-to-consumer trace. Trace timestamps are Z80 T-states, and trace buffers can overrun: check `overrun` and paginate before treating a capture as complete. [Gearsystem MCP reference](https://github.com/drhelius/Gearsystem/blob/3.9.18/MCP_README.md).

Gearsystem's I/O implementation injects 32 Z80 T-states after an SG-1000 PSG write. Treat this as a specific emulator timing choice; retain those events when measuring game cadence or comparing another emulator. [Gearsystem I/O implementation](https://github.com/drhelius/Gearsystem/blob/3.9.18/src/SmsIOPorts.h).

## How this changes ROM reconciliation

1. Trace VDP register setup and every bulk/data-port writer; record caller argument triples and the physical source offsets. Decode VRAM tables at named checkpoints. Mark source spans as transfer sources first, then split them into patterns, colors, names, sprites, or encoded data only when the format is proved.
2. Trace PSG writes backward through the channel engine and its ROM pointer reads; establish event formats, terminators, and stream extents before labelling a sound asset.
3. Trace `$DE/$DF` probe and `$DC/$DD` scan separately on an emulator that models SC keyboard hardware. Compare its observed port values to Gearsystem's controller-only path. Keep SG gameplay authoritative but document where the game expects SC input.
4. Use runtime PC coverage to confirm instruction boundaries and find entry points, then use control flow, call arguments, pointer tables, and hardware consumers to settle unexecuted regions. Preserve unknown bytes as unknown; do not turn an unvisited span into either proven data or unreachable code.

The next concrete capture should be a short VDP register/data and PSG trace from reset through title, paired with register and VRAM snapshots. That will let the graphics and sound consumers drive the next evidence-backed ROM annotations.
