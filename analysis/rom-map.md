# Champion Tennis G-1009 ROM: historical investigation map

This file preserves the initial tool experiments and reference captures. Its intermediate counts, open questions, and next-step instructions are historical. The preliminary Ghidra import scripts, project, candidate map, and block-suggestion outputs were retired after the current disassembly was established; commands for those files below no longer run. Use [WORKLOG.md](../WORKLOG.md) for current status and [static-rom-review.md](static-rom-review.md) plus [annotation-audit.md](annotation-audit.md) for the present disassembly classification.

**Current static review:** [static-rom-review.md](static-rom-review.md) is the whole-ROM structural annotation and supersedes the historical classification totals in this initial map. It records 5,765 code bytes, 2,427 byte-emitted bytes, 2,413 bytes with direct data evidence, and 14 byte-emitted bytes without a proved reader. This review used no emulator.

This is a bounded first pass over the identified 8 KB cartridge. `scripts/analyse_rom.py` imports a byte-identical private copy at Z80 address `0000` into an ignored Ghidra project and exports candidate instructions to `build/analysis/z80-candidate-instructions.tsv`. Ghidra found 880 candidate instructions after seeding reset. This is a control-flow hypothesis, not a complete code/data classification; indirect dispatch and unmapped/mirrored addresses can hide reachable code. Keep future labels and evidence here rather than editing generated output.

Interpret I/O and ROM source spans against the [SG-1000 / SC-3000 architecture reference](sg-sc-architecture.md). In particular, follow VDP and PSG consumers before promoting unknown bytes to graphics or sound data; Gearsystem's SG input route does not implement the SC keyboard port writes.

`scripts/roundtrip_rom.py` disassembles the locally configured 8 KB image with native `z80dasm` 1.2.0 at origin `0000`, assembles its generated listing with native `z80asm` 1.9, and byte-compares the result. Both the original linear pass (`--linear`) and the current provisional code/unknown pass reproduce all 8,192 bytes and SHA-256 `19bb6647f14ef50f976e8d0a06d389f06b2e700d54a54fb1734d3140f9745ad1`. Listings and reports are ignored under `build/analysis/`. Byte equality proves preservation of the input bytes, not correct interpretation.

**Precise round-trip midpoint:** The original all-instruction listing is `build/analysis/champion-tennis-linear.asm` (`--linear`). It contains Z80 mnemonics, generated labels, and byte comments, with no data directives. The default listing, `build/analysis/champion-tennis-classified.asm`, uses checked-in [rom-blocks.def](rom-blocks.def) and [rom-symbols.def](rom-symbols.def): 4,722 bytes are candidate/observed code, and 3,470 bytes are emitted as `defb`. Of those byte-emitted bytes, 1,962 have specific data evidence in [rom-data-evidence.tsv](rom-data-evidence.tsv), while 1,508 remain unclassified. Neither listing includes the original ROM; the assembler reads the text alone.

### Reset-to-title hardware trace, 120 frames

`python .\scripts\smoke_gearsystem.py --hardware-frames 120` saves an ignored VDP/PSG trace, VDP and PSG state, and the full 16 KB VRAM snapshot. The capture contains 61,315 events with no trace overrun. `python .\scripts\check_vram_sources.py` verifies the ROM hash, SG-1000 media mode, captured VDP registers, and these byte-for-byte source/destination matches:

| ROM source (end exclusive) | VRAM at title | Length | Interpretation |
| --- | --- | ---: | --- |
| `$19CC–$1DCC` | `$1800–$1BFF` | 1,024 | Sprite-pattern source; VDP register 6 is `$03`. |
| `$1C4C–$1F94` | `$2098–$23DF`, `$2898–$2BDF`, `$3098–$33DF` | 840, repeated three times | Background-pattern source reused across the three Graphics II bands; VDP register 4 is `$07`. |
| `$01C3–$01D3` | `$0000–$034F`, `$0800–$0B4F`, `$1000–$134F` | 16 encoded bytes yield 848 bytes in each band | Graphics II color runs; high nibble is color value, low nibble is count of eight-byte repetitions; final zero terminates the stream. |

The two source spans overlap from `$1C4C–$1DCB`; those physical ROM bytes have two observed graphics uses. The code at `$00AD–$00B6` supplies the sprite copy's source, destination, and length to `$029D`. The calls at `$0088–$0091` supply 72 bytes from `$1C4C` and then 768 bytes from `$1C94` to the same copier; the VRAM snapshot verifies the combined 840-byte stream in all three pattern banks. The evidence file records the union without counting overlapping ROM bytes twice. The screenshot alone could not establish these relationships.

The loop at `$009A–$00AC` reads bytes until the zero at `$01D2`. For each nonzero byte it writes its high nibble to VRAM eight times per unit of the low nibble through `$02E4`/`RST 8`; the 15 runs expand to 848 bytes. Later `RST 30` copies the first `$0800` VRAM bytes to `$0800` and `$1000`, so the color runs occur in all three bands. The checker validates the expanded bytes against all three locations. The remaining bytes in those color banks need their own source analysis.

The register trace writes R2=`$0E` during initial setup, selecting a name table at VRAM `$3800`, then writes R2=`$0F` before the frame-120 title capture, selecting `$3C00`. Earlier references to `$3800` as *the* name table need this phase qualification. The captured title values are R0=`$02`, R1=`$E2`, R2=`$0F`, R3=`$7F`, R4=`$07`, R5=`$76`, R6=`$03`, R7=`$01`. Only four PSG events appear in this reset/title trace: attenuation `$F` (off) for noise channel 3 and tone channels 2, 1, and 0. Music/event-stream interpretation remains open.

### Title name table, sprite attributes, and transformed sprite patterns

`python .\scripts\check_title_layout.py` checks the frame-120 VRAM against ROM-derived output and saves `build/analysis/title-layout-report.json`. Reset code `$00B9–$00EA` calls `$055F` twice: each call copies 26 16-byte slices from alternate halves of 32-byte ROM blocks beginning at `$19CC` and `$19DC` into RAM `$C090` and `$C080`. It then reverses the bits in each of the resulting `$340` bytes and copies the full `$400`-byte RAM buffer to sprite-pattern VRAM `$1C00`. At frame 120, 831 of the 832 ROM-derived bytes agree; VRAM `$1C03` is `$FB` where the transformed ROM source yields `$00`. `python .\scripts\check_sprite_counter_alias.py` verifies the exception: the CPU trace at frame 34 writes `$00` to RAM `$C083` in the bit-reversal loop; interrupt code at `$06C2` then decrements that same byte in frames 35–39 (`$FF`, `$FE`, `$FD`, `$FC`, `$FB`). The frame-39 CPU trace shows `$02A5` reading `$FB` from `$C083` with destination `$1C03`, followed by `$02A6` writing `$FB` to VDP port `$BE`; the hardware trace confirms VRAM `$1C03 <- $FB`. Thus all 832 transformed positions are explained, with byte 3 dynamically changed by the countdown before upload. The remaining 192 uploaded bytes depend on RAM contents outside the `$340`-byte transform and are not attributed to ROM here.

The routine at `$01D3–$01DC` writes the sprite terminator value `$D0` to VRAM `$3B00` and `$3B28`; `$046F–$0477` later copies 40 bytes from RAM `$C010` to `$3B00`. At frame 120 the first 40 bytes are `$D0` followed by zeroes. A 400-frame no-input trace, checked by `python .\scripts\check_sprite_attributes.py`, captures 38 complete 40-byte uploads beginning after observed VINT 354; each covers exactly `$3B00–$3B27`, and the last agrees with frame-400 VRAM. The 40 bytes form ten hardware sprite-attribute records of four bytes each (Y, X, pattern number, colour). This proves the buffer-to-VDP path and its changing output, though record roles and motion still need input-correlated traces.

For the name tables, `$0407` clears `$3800–$3AFF`, then `$040D–$045E` copies seven fixed-width ROM row groups (232 bytes in total) through `$0542`, stepping the VRAM destination by 32 bytes per row. The high byte of `BC` is each row's width, and the low byte is the row count; an earlier analysis had these reversed. `python .\scripts\replay_title_vdp.py` replays all 61,270 VDP/PSG/IRQ trace lines to reproduce the frame-105 VRAM exactly, finds all 60 row write sequences byte-for-byte in the VDP log, and verifies that all 232 copied positions still match at frame 120. `$02EF` clears `$3C00–$3EFF` before constructing the title table. `$05DA` expands four packed masks from ROM `$0376–$03B9`: each set bit, read most-significant first, writes a selected tile index at its corresponding title name-table position; clear bits leave the prior tile untouched. `python .\scripts\check_title_bitmap_masks.py` verifies all four ordered VDP write sequences: 85, 56, 3, and 9 writes of tile `$69`, `$69`, `$62`, and `$64` respectively. The latter two overlay the first mask's region. Three direct tile-index strings copied by `$0357–$0373` from `$03BA`, `$03D5`, and `$03EE` match VRAM `$3E03`, `$3E64`, and `$3EA4` byte-for-byte at frame 120. Frame-90 is blank and frame-105 already equals frame-120 VRAM. In the frame-105 trace, name-table clearing starts after observed VINT 91; the first nonzero name-table write follows VINT 94 (`$38AA <- $09`). Clearing the second table spans observed VINTs 95–98, and its title writes continue through VINT 99.

The court traces execute `$06B1` and `$17C5` once in each of the three sampled frames. `$06B1` increments the byte at `$C06B`, cascades further counter increments, decrements `$C083`, and calls `$17C5` when that countdown reaches zero. `$17C5` starts `B=2` and uses `$198D` to compute `$C085 + 14*B`; the trace observes record bases `$C0A1`, `$C093`, and `$C085` before the loop exits. This is **audio work, not yet the gameplay update**: `$1787–$17B8` initializes three 14-byte records at those RAM addresses, copies a 12-byte ROM template from `$17B9–$17C4` into each, gives them separate RAM buffers at `$C0AF`, `$C0CF`, and `$C0EF`, and jumps to `$1974`, which emits maximum-attenuation values through port `$7F`. `$1833` also calls the port-`$7F` writer at `$197D` while processing a record. The trace observes `$182A` reading ROM bytes at `$19BD` and `$19C0` via the record-held stream pointer. The sound stream's full extent and encoding remain unresolved. Three isolated samples do not establish the full audio cadence or gameplay cadence.

### First audible PSG event

The 400-frame no-input hardware trace records seven short tone-channel-2 pulses after the initial mute. Each pulse uses PSG period `$054`; volume alternates between attenuation `$0` and `$1`, with `$F` between pulses. `python .\scripts\smoke_gearsystem.py --cpu-window-start 356` captures the first pulse's CPU path. `$1944–$1972` indexes a 12-word, big-endian pitch table at ROM `$18DA–$18F1`. The observed lookup reads `$2A70` at `$18E2–$18E3`, shifts it right by `C & 7 = 3` to `$054E`, and emits PSG latch `$C4` plus data `$05`, yielding period `$054`. `python .\scripts\check_psg_pitch.py` verifies these CPU and PSG observations. This identifies the pitch lookup and output encoding for one event; command bytes, duration encoding, and the full stream boundaries remain open.

`python .\scripts\smoke_gearsystem.py --cpu-window-start 356 --cpu-window-frames 11` captures the whole first sound without a trace overrun. `python .\scripts\check_first_sound_stream.py` verifies 22 consecutive ROM reads at `$1FDD–$1FF2`, all seven audible pulses, and the final mute. At `$1840–$185A`, the command high nibble selects one of eight 16-bit handler addresses from ROM `$185B–$186A`; the low nibble remains in `C`. `$23` selects `$18F2` and stores pitch shift 3; each `$05` selects `$186B`, where low nibble 5 selects pitch-table index 4. `$3F` and `$3E` select `$1905`, storing attenuation 0 and 1 in record byte `IX+6`; the next note command emits that level. Thus seven `$05` commands produce attenuation `$0,$1,$0,$1,$0,$1,$0`, all at period `$054`.

The setup bytes `$58`, `$70 $01`, and `$60 $01` set record byte `IX+5=8`, global audio tick reload `$C082=1`, and record byte `IX+8=1`. On each note/rest command, `$18B0` stores `IX+12=1`; `$18C1–$18D0` computes `IX+13=2` from the base and scale. The final `$00` takes the low-nibble-zero rest path at `$187B`, emits channel-2 mute `$DF`, and no further sound is observed through frame 400. This explains the first sequence's cadence and volume behavior. The general meaning of these fields for other streams, and the record deactivation rule, still require more cases.

### Two-channel court sound after button 1

`python .\scripts\smoke_gearsystem.py --hardware-frames 620 --hardware-button 1 --hardware-press-frame 120 --hardware-hold-frames 300` records 63,475 filtered hardware events, including 357 PSG events. The first seven channel-2 pulses are the same sound as the no-input capture. Starting around hardware timestamp 25,556,007 (near frame 428), channels 1 and 0 sound together and step through descending-volume envelopes. The hardware capture alone does not establish that this is active match play.

`python .\scripts\smoke_gearsystem.py --cpu-window-start 427 --cpu-window-frames 6 --cpu-window-button 1` reproduces the input schedule and captures both first notes. At `$19B8`, record `IX=$C093` reads `$1F53` to `$1F5A`: `41 57 70 02 60 08 22 01`; record `IX=$C085` reads `$1F05` to `$1F0D`: `41 57 70 02 60 04 22 8A 08`. These are observed stream prefixes, not complete stream boundaries. Both use `$41`, `$57`, `$70 02`, and `$22` setup. In the first record, `$01` selects pitch-table word `$3570` at `$18DA` and shift 2 produces `$0D5C`, emitted as PSG channel-1 period `$0D5`. In the second, `$0A` selects the word at `$18EC` and shift 2 produces `$07F0`, emitted as channel-0 period `$07F`. This independently exercises the pitch table, shift, and output encoding on two channels. The later stream contents, the `$8A` command's meaning, and record termination remain to be traced.

Both stream prefixes fall within the `$1C4C` to `$1F94` background-pattern transfer already verified against VRAM; the ROM bytes are used both as graphics and sound data. This does not change the count of bytes with direct data evidence.

Later focused button-1 CPU windows at frames 460-465, 540-545, 900-905, 906-925, and 926-949 show further reads from both records. `$8A` at `$1F0C` dispatches to the ordinary note handler at `$186B`: low nibble `$A` selects pitch-table index 9, and shift 2 produces `$07F0` from the `$1FC0` table word at `$18EC`, matching PSG channel-0 period `$07F`. This is a note command, not a stream control byte. Record `$C085` reads `$00` at `$1F52` in frame 920; record `$C093` reads `$00` at `$1F96` in the later window. Both zero bytes take the rest/mute handler and emit PSG attenuation `$F` on their respective channels. The transition is now traced for both records: in `$19AE-$19B3`, the current index increments from `$4E` to the `$4F` length for `$C085`, or from `$44` to the `$45` length for `$C093`, and is reset to zero before `$19B8` reads the final byte using the pre-increment index held in `C`. On a later audio update, `$19A8` compares that zero index against the zero stop field at record offset 3; `$19AA` skips the fetch with carry set. No further byte is fetched from either stream in frames 1000-1005. Thus the final `$00` supplies the mute/rest command while the length wrap plus equality check stops subsequent fetching. `$1F96` is the only newly proven data byte here outside the already proven graphics span.

## Repeatable execution evidence

`python .\scripts\check_source_repeat.py --button 1 --hold-frames 300 --after-frames 30` starts from reset in two separate Gearsystem 3.9.18 headless processes. At frame 120, both show the title. Holding P1 button 1 through another 300 synchronous frames reaches the tennis court; both runs then have identical 1 KB RAM hashes and screenshot hashes after release plus 30 frames. The full report and captures stay under ignored `build/reference/button-1/`.

The title visibly says `1PLAY == PUSH INS/DEL KEY` and `2PLAY == PUSH FUNC KEY`. A long P1 button-1 hold reaches a court display, but that capture does not establish active play: at release plus 30 and 60 frames the CPU repeatedly waits at `$05C3` for audio channel state, and at release plus 2,000 frames it has returned to the `$012E`–`$016A` menu loop while the court remains visible. There the trace loads `$C03D=00`, so both the bit-5 and bit-2 branches return to the loop; a late second button-1 press leaves it there. A long left hold also reaches a court, now visibly marked `DEMO`; its post-release trace reads `$C03D=04`, enters the input check at `$016C`, and adds executable addresses but does not prove the match loop. Pressing P1 button 2 for 300 frames reached a court capture identical to button 1 at the earlier checkpoint. Controller-to-mode mapping, playable entry, and two-player mode remain unproved. Gearsystem's exposed MCP controller tools do not include keyboard injection; the title's keyboard prompts therefore need further input-path investigation.

## MAME keyboard mode and scored-point evidence

MAME 0.289's SC-3000 configuration loads the same verified cartridge through its software list and exposes the SK-1100 keyboard. The scripted `scripts/capture_mame_modes.lua` holds Del/Ins or Func from frame 120 to 420 and saves 1 KB RAM plus a screen PNG at selected frames. At frame 600, no key gives `DEMO` and `$C03D=04`; Del/Ins gives `1PLAY` and `$C03D=00`; Func gives `2PLAY` and `$C03D=80`. The older Gearsystem court captures did not establish these distinctions because its SG keyboard output path is absent.

With Del/Ins mode selected, a P1-left hold from frame 1300 to 1450 moves the bottom player from about X=212 to X=148 by frame 1500, with seven RAM bytes differing from a same-schedule no-input run. A P1-button-1 hold over the same interval changes `$C03D` to `$08` and the displayed score from 0-0 at frame 1200 to B:15 at frame 1500. This is direct evidence of responsive player input and a scored point. The ball and score RAM fields remain unassigned; the later write trace below identifies the player-X field and a checkpoint for its update path. The later focused ball trace below captures the launch, one return, and this scored point.

`scripts/trace_mame_player.lua` repeats the one-player/left schedule and samples frames 1280-1500 plus writes to `$C04A`, `$C04E`, `$C035`, `$C021`, and `$C06B`. Its check validates 221 samples and 1,363 writes. `$C04A` is the input-responsive bottom-player base X: it moves from `$C0` to a clamped `$80` through 43 writes at MAME post-write PC `$143B` (ROM `LD (DE),A` at `$143A`). `$148C` computes a movement step of `1 + ($C06B & 1)`. During this window the ball follows that player: `$0B8A-$0B91` sets ball X `$C04E=$C04A+$14` and copies it to `$C035`; `$13F3-$13F9` copies the ball-sprite bytes `$C04D-$C050` into one of the sprite records, observed at `$C021`. These ball X destinations receive five writes per frame across the 220-frame write window. The interrupt callback at `$0699` calls `$13B9` through `$06AE`, then falls through to `$06B1`; its `$C06B` write occurs once per frame after the observed player and sprite-buffer writes. Thus `$06B1` is a post-court-update checkpoint for this path. The left trace establishes player movement and an attached ball position, not independent ball flight or the cadence of every subsystem.

`scripts/trace_mame_score.lua` holds one-player selection from frames 120–420 and P1 button 1 from 1300–1450. It samples score/state bytes each frame from 1200–1800 and taps writes to `$C03D–$C044`; `scripts/check_mame_score_trace.py` validates 601 samples and 38 writes. The only write to either score candidate `$C03E/$C03F` in that window occurs in frame 1433: `$C03F` changes `$00→$01` at MAME post-write PC `$0A31`. ROM instruction `$0A30` is `INC (HL)`. The same frame writes `$08` to `$C03D`, and the frame-1500 screenshot shows B:15 while A remains 0. The scoreboard renderer reads `$C03E` and `$C03F` at `$0760` and `$0769` and draws them at separate name-table locations. This supports `$C03F` as B's point-unit state and `$C03E` as A's corresponding field.

A static control-flow pass promotes `$098F–$0AA1` from byte emission to code. At `$098F–$09A1`, bits of `$C039` select an outcome value; `$09A2–$09CB` combines it with `$C042` flags. `$09CE–$09F4` starts with the two point addresses in HL/DE and conditionally swaps them according to the outcome and `$C039/$C03D` flags. `$09F5–$0A08` branches on the selected score's low three bits. The paths at `$0A30/$0A33/$0A3A` increment a selected field, inspect the opposing field, or transfer a unit between fields; `$0A3F–$0A78` increments one of `$C040/$C041`, compares it with six, resets `$C03E/$C03F`, and sets status bits. `$0A79–$0AA1` has additional countdown/state transitions using `$C06C`. These instruction paths have consistent boundaries through the prior code at `$0989` and following code at `$0AA2`, with no direct data evidence overlapping them. `python .\scripts\roundtrip_rom.py` still rebuilds the exact 8 KB image: code classification rises from 3,333 to 4,722 bytes, including the `$0B41` to `$0B5D` ball/serve state dispatch. The precise tennis interpretation of each branch, including deuce/advantage and whether `$C040/$C041` count games, remains provisional until matched to controlled scores.

The next per-frame call at `$0B29` loads IX with `$C03A` and dispatches on state bits 7 through 1. Its `$0B41` to `$0B5D` continuation, previously byte-emitted, contains direct `BIT`/conditional-`JP` pairs into `$0BEB`, `$0D47`, `$0D61`, and `$0BF3`; it is now classified as code. Other branches lead to `$0B5E`, `$0B7A`, and `$0BBC`. The `$0B5E` path reads player base X `$C04A`, calls `$1760`, resets `$C039/$C06C`, and sets state bit 6. The `$0B7A` path calls `$12CE` for ball motion and, while the ball remains attached, sets ball X `$C04E=$C04A+$14`. The nearby `$0B73` to `$0B79` bytes are referenced as a data table and remain byte-emitted.

The ball-motion code is more direct than the left-input trace suggested. `$11A0` dispatches on `$C038` flags; its `$11C5` path copies six trajectory bytes from `$C057-$C05C` to `$C060-$C065`, clears elapsed step `$C066`, and switches flags for flight. The `$11E0` path calls `$12CE` each update. There `$C066` increments; `$C060/$C061` pass through `$136B` to produce X/Y displacements from bases `$C064/$C065`; the results become court-plane X/Y `$C035/$C034`. Later in the same routine, `$C04D` receives a height-adjusted Y using `$C063` and a calculated arc, while `$C04E` is the sprite X. `$13F3-$13F9` copies `$C04D-$C050` to one of three sprite records. Thus `$C034/$C035` track court-plane ball position and `$C04D/$C04E` feed the ball sprite. The numeric units, arc equation, and collision conditions at `$11E0-$12CD` still need careful annotation. The no-input and button-1 RAM captures are consistent with separate court-plane and sprite Y values; the focused flight trace below confirms the initial per-frame step and the transition to a returned trajectory.
