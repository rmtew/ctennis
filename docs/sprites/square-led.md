# Selected square LED scores

The later [framed layout](score-layout.md) supersedes the positions and alignment
below. The selected segment shapes and startup-bank design remain in use.


The user selected “lock in square” from Library preview
`libfile_154a4a5e61f48191b284c13acd5b18aa`, version0. The implementation preserves
those exact pixels, including the right-aligned zero, centred single A and blank
opponent score. Indices0–6 remain 0,15,30,40,A,40,blank. Both digit slots remain
16x16 at x16/224,y40. The A/B headings, controller labels, six WIN rows, frame,
palette, scoring rules and live field selection are unchanged.

`amiga/square_score_banks.i` draws seven one-bit masks into a reused32-byte stack
scratch area. It copies existing court rows40–55 into each of the28 point banks
and replaces only the selected side's16-bit word on each row. Construction runs
once before title setup and the simulation clock. All point pointer symbols and
512-byte per-variant strides are retained. The four streams occupy the same
14336 bytes of chip RAM, now declared in BSS rather than stored in the executable.
Score changes continue using the unchanged PR19 pointer patcher: no new rendering,
allocation or bank writes occur during play, restart, attract mode or navigation.

The48-byte definition is copied directly from the accepted square preview's
serialized definitions:28 rectangle bytes,6 character segment masks and14 state
selectors. Four stream descriptors add40 bytes; constructor instructions are216
bytes and its startup call4 bytes. Thus added resident code/data is308 bytes
before hunk alignment/loader overhead. The existing4096-byte application stack
supplies32 scratch +60 saved registers +4 return-address bytes; no new persistent
scratch allocation is required. Bank RAM does not shrink. The removed28 stored
strips total14336 bytes. Executable savings also depend on relocation/symbol/hunk
metadata; executable size must not be described as free-RAM savings.

The frozen contract contains224 bytes of expected pixels sampled from the
selected comparison PNG (SHA256
`4508697e2cc7999b151d38cff4270bf5bebc9da76c77511245756ff17e9ec7df`). These expected
pixels are not generated by the runtime or loaded by the product. Full-width
checks also protect the copied court pixels outside each score. The initial zero
on three static court planes changes only inside the two approved point cells;
plane1, all A/B/WIN artwork and the palette are byte-identical to the PR19 base.
