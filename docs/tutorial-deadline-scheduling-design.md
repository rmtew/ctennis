# Tutorial deadline scheduling proposal

Analysis only; no production scheduling change, new native capture, upload or merge. Source reviewed: PR41 product `a936ebac16c977cfc6c39a4426de1cbfdf62170e`, documentation head `9c85f5a24c84970efde8f34f09ff0c1e40359f89`. The user's direction is sound: service live devices when necessary, reserve visible work, and give bounded prediction the remaining time. It needs both simulation and physical-field deadlines, not just a larger operation quota.

## Current responsibilities and redundant work

| Work | Current source / purpose | Proposed treatment |
|---|---|---|
| Keyboard transport | `main_loop` / `game_poll_keyboard`: CIA serial read, matrix update, timed acknowledgement with CIA interrupts disabled | Keep a bounded service deadline. Pump at scheduler entry and between admitted chunks when due. Do not rescan logical/UI input for every serial pump |
| Joystick and logical/UI sample | `simulation_update`: `sample_amiga_joystick`, `ui_sample`, `game_native_commands`, `tutorial_controls` | Once per nominal update by default. Preserve held/edge/release, entry filters, menu gestures and repeat timing. Extra urgent samples require explicit edge accumulation, not repeatedly calling today's edge-clearing `ui_sample` |
| Presentation service | `main_loop` and line253 Copper IRQ call `poll_presentation` | Preserve IRQ and bounded visible/blank phase observations. Frequent no-ready/unchanged-beam polls are candidates for removal after phase/latch proof |
| Clock accounting | `account_sim_timer` in main loop; remaining-time checks use coherent CIA reads | One clock owner maintains the continuous epoch. Read/account when servicing deadlines; repeated reads alone are not useful progress, but are required at every bounded yield for safe admission |
| Replayed input/poll/result envelopes | `game_preview_execute_record` and synthetic `game_round_poll_body`, pad/result bodies | Preserve exact original ordered operations, cursors, edges, lifecycle/entropy effects and per-envelope checks. These are simulation inputs, not hardware polling and cannot be deleted merely because the user has not moved |

The retained fresh incoming analysis shows about 281/285 ms in observed polling outside callbacks, but that includes real service, IRQ/contention and timing-loop activity. It is neither all redundant nor an available CPU budget. The replay's 161 non-dispatch envelopes occupy 75.6% of its entered operation slots but only about 6 ms actual bus time. Avoid conflating those two forms of polling. See [the cost analysis](tutorial-incoming-analysis.md).

Unchanged keyboard/UI matrix scans are also candidates for a dirty-generation fast path, but only after preserving releases, alias independence, tutorial input-source selection and entry filters. A held movement key still needs its due repeat/gesture clock even when no device bit changes. Keyboard transport must continue for all keys/releases while paused, not only currently relevant menu actions. No scan savings are measured here.

Two existing details forbid simply deleting main-loop polls. `game_poll_keyboard` times acknowledgement with `last_timer_count`; a pump must receive a current accounted clock, rather than many chunks using an old acknowledgement age. `poll_presentation` clears `blank_seen` only on an observed visible line. A line253-only IRQ never supplies that observation, so the current once-per-field latch would stay set. It also polls again within the publication window when a completed scene becomes ready after the IRQ. The replacement must deliberately re-arm in the visible field and service a new completed ready bank during the safe window; retain current polling until that is proven.

## Deadline ownership

The native main-loop scheduler owns time admission. It retains the existing continuous CIA epoch, fractional simulation interval and callback start/completion bookkeeping. The presenter owns the guarded beam transaction and bank retirement; no prediction runs in the IRQ. Preview owns private simulation contexts and yields with history metadata restored; it does not choose wall-clock deadlines.

Simulation and display clocks are different. Both standards simulate about59.923 updates/s; PAL displays50Hz, NTSC60Hz. Existing simulation intervals are11838+14906/65536 and11947+13180/65536 E-ticks. Physical publication starts at line253 and last safe lines are307PAL/257NTSC, with the existing four-line guard. A scheduler must preserve these relationships, rather than assume one callback equals one field or silently convert PAL simulation to50Hz.

Define a scheduling cycle's next nominal callback deadline `D_tick` and next intended completed-scene handover `D_ready`. Derive the latter from coherent physical beam/field tracking and the existing standard; prepare before the selected line253 opening conservatively until a tighter producer cutoff is measured. A producer already ready in the safe window can be handed over immediately. Missing a producer cutoff retains the front bank; it does not relax the guard or recycle the displayed bank. If ready after the current field's publication, target the next field explicitly.

The earliest service deadline also includes `D_input`, the next required hardware pump/sample. A chunk must satisfy all relevant deadlines independently: for each deadline `D_i`, current time + measured chunk bound + still-required tail for that deadline + margin <= `D_i`. This avoids subtracting every tail twice or forgetting a render/input tail merely because a callback has spare time. All costs use E-ticks consistently, with bus CCK converted using the standard's timer relationship. A past deadline admits no optional work; keep servicing mandatory input/presentation and record the miss.

No numerical reserve is approved yet. Measure actual tails separately by phase: keyboard read/ack and clock service; joystick/UI/control and request/cancel paths; generation qualification; sprite/header/marker/plane writes and `complete_scene`; `complete_update`; presenter IRQ including nested interference. Dirty footer/menu raster needs its own bounded job, not a hidden tail in every cheap worker. Avoid double-counting IRQ cost if the chunk measurement already includes its conservative interference allowance. Do not use observed means or pair sums as maxima.

## Priority and bounded execution

At each public yield, re-read time, service due input/presentation, validate generation, and select the highest eligible task:

1. Mandatory keyboard/presentation service, input sample due at its original update time, and cancel/resume/menu state changes. Finish callback bookkeeping before starting background work.
2. Prepare/publish due visible work: changed placement, the selected alternative's ready endpoint/marker and any already-due normal-speed samples. Only complete generation-owned banks can become ready; stale markers retire on edits. Due publication takes precedence over optional prediction.
3. Produce the selected endpoint: required historical resolve/PRIME/incoming contact first, then the existing bounded endpoint query when eligible. A query rejection leaves exact sequential continuation. The selected endpoint has priority over the other alternative.
4. Supply the next selected samples ahead of their due time. Keep the current outcome/availability qualification and normal-speed/dwell clock (two nominal callbacks per animation advance and 30 for terminal dwell) unless separately reviewed. Prediction may run ahead privately; it must not advance visible playback whenever a worker finishes. Once playback is due, its preparation/publication is mandatory visible work in priority 2. Endpoint priority must not monopolize repeated cycles after ready or block already-due samples.
5. Compute the other alternative, then nonurgent trail/footer work. Menu-open behavior continues to suppress background prediction. Do not let optional raster work run ahead of selected endpoint/sample readiness just because it was queued first.

Stop a chunk at an original envelope boundary, actual contact/terminal/lifecycle/generation change or its measured cost ceiling. Re-sample deadlines before starting another. Cheap operations can be grouped when a known whole-group upper bound fits; expensive dispatch/query/raster phases use their own bound. Neither 'four operations' nor 'four slices' is the time budget. Keep a structural maximum operations-per-call as a safety ceiling, plus measured maximum elapsed cost and a conservative smaller-chunk fallback. An observed overrun is a failing acceptance condition and disables that optional class; checking elapsed only after an indivisible expensive operation cannot undo a missed deadline.

Start with repeated existing one-to-four-operation calls. Use an audited per-phase/record-pattern cost table including request/PRIME, dispatch, irregular retained prefixes, contact/miss and transitions; where classification is uncertain use the worst supported class or the current conservative fallback. No preemption inside actual bodies and no device access from the standalone core. A later guarded packet can group more cheap envelopes only if measured public-yield overhead remains material. It still executes original bodies in order and performs every existing post-envelope check; it does not skip no-op-looking input to spend slots faster.

## Responsiveness and live isolation

A physical keyboard pump updates transport state only. Consume logical edges/controls at the next nominal sample; do not repeatedly clear or consume them while predicting. If an earlier Escape/resume or placement-change response is desired, add a bounded pending-intent path with press/release accumulation and explicit single consumption, then prove existing aliases, entry suppression and gesture behavior. Do not restore private replay state into the live canonical match to inspect input.

A due service check between every chunk bounds transport responsiveness by the maximum nonpreemptible chunk plus service delay; logical intent by that delay plus the chosen sample interval. Establish an acceptable input/pump gap and actual serial buffering/ack behavior before enlarging chunks. A pending key that has not been pumped cannot be assumed absent. On an edit, coalesce latest placement at the original repeat cadence, cancel/increment generation, invalidate pending ready endpoint/raster jobs and start from the selected frozen context. Resume/title clears background ownership before the next live dispatcher. Service callbacks never enter while A5/private history ownership is active; use the existing public release boundary.

Prediction can use otherwise idle main-loop time after `complete_update`, rather than forcing all work through `tutorial_tick`. Keep the currently displayed bank immutable and mark any background scene ready only after its entire producer job is complete. Current `complete_scene` uses update-generation bookkeeping, so introducing background rendering requires an audited completion owner; begin with background prediction only and retain publication at the existing callback path. This limits the first change and still creates useful extra compute opportunities. Deadline ownership changes must not reset simulation phase or hide overdue callbacks.

## API size and staged proof

Existing `game_preview_step(generation, 1..4)` already performs exact original bodies, checks outcomes after each envelope and releases private ownership. It can support time-based admission, bounded calls and work between nominal callbacks with a small native scheduler change; a new packet ABI is not required for that first proof.

It cannot currently supply full selected-first computation merely by giving it more budget. `game_preview_desired_variant` derives held/released owner from global status; PRIME orders both contexts, and `game_preview_finish_variant` assumes held completes before released. The UI selection affects presentation and endpoint querying, not that computation order. Selected-first needs a focused owner-policy extension with per-variant completion state and preserved independent cursors/contexts. Keep a deterministic legacy default for existing callers. This is separate from a guarded packet and must not reuse a later full318 by patching X/Y. Final geometry/result readiness still requires both completed alternatives; progressive selected publication does not.

Suggested increments, requiring user review before runtime implementation:

- First calibrate current worker chunks and mandatory tails under real production scheduling; use the retained analysis as a prior, not a timing bound. Prove four-operation chunks without changing core bodies or input cadence.
- Then implement one native deadline owner and due-only live service, initially retaining presentation polling and callback rendering as conservative fallbacks. Use between-callback prediction, exact clock accounting and bounded service gaps; preserve current chunk maximum until measurements justify more.
- Extend variant ownership for selected-first endpoint and selected sample lookahead. Only consider a packet if attribution still shows enough yield overhead to justify its extra proof burden.

## Minimum acceptance evidence for a scheduling change

No broad campaign is requested now. The future focused minimum must include:

- Actual shared-core CPU comparison of complete318, ordered events, per-variant cursors/counts/outcomes/launch seeds across one/two/four-operation grouping, interleaved variants and irregular recorded prefixes. Poison private working state; test selected held/released, switches mid-computation, canceled/stale generations, seek exclusion and resume neutrality. Scheduling must not change RNG/event order within either branch.
- PAL and NTSC production-context native captures through physical controls, with real incoming contact/miss, both ends, upper/lower handoff, short/long/net/out/fault paths, AI/RNG and audio/lifecycle expensive cases; include first request, held movement, fresh press/release, variant switches, menu/resume, footer/menu dirty and keyboard acknowledgement during a long chunk. Cover field-window opening/closing and simulation/display phase drift, not just one favorable callback phase.
- Measure every complete callback, worst indivisible job/chunk, service gap, mandatory tail, IRQ interval, stack and chip RAM. No hidden observer epoch resets. Verify accounted elapsed, nominal callback cadence and zero missed guarded COPJMP deadlines; where no new scene is due, retaining the front is legitimate and must not be counted as a frame drop. Where animation/placement is due, verify timely actual completed-bank publication, phase progression, actual pixels/sprite headers and DMA ownership, not only counters. Distinguish finite zero observed drops from a universal bound or WinUAE/hardware claim.
- Negative controls: deliberately oversized chunk/tail or delayed input service must fail the respective deadline/gap contract; stale generation must fail publication qualification. A test that cannot detect those faults is insufficient. Compare same recorded input/seed for branch equality; independent live-entropy runs are not paired performance experiments.

The integrator owns scheduler implementation/evidence after approval; an independent reviewer checks cost classes, deadline ownership, variant equivalence and actual publication. PR41 remains draft/unmerged. Appearance, full resource profiles and cold stripped-release gates remain open. This proposal makes no measured speedup, no-drop or release claim.
